大模型期末大作业课题指南
面向本科四年级学生　　2026年9月
本指南提供15个大模型相关实践课题。每组选择一个课题，一个课题由一个小组承担，每组不超过5人。各组应围绕明确问题完成程序实现，通过对照实验检验方法，并说明系统的局限与实际成本。
分组与资源条件
建议每组3至5人，可根据实际人数合并职责。课题基础版按普通电脑和有限 API 预算设计，不要求独立 GPU。第7题需先验证代码隔离环境，第13题需具备一定 PyTorch 基础，第14题需先完成本地模型试跑。
选题时提交课题编号、成员、分工、数据来源和拟采用的基本方案。时间节点、提交平台、具体 API 额度及配套材料以课程通知为准。
工作方式
先实现能够完成基本任务的基线，再提出有依据的改进。界面以便于使用和核查为目的，不要求复杂前端；只展示聊天记录或更换现成项目名称，不足以说明完成了课题。
建议按4至6周安排课外开发。课内实践用于选题指导、基线检查、中期讨论和答辩展示；不要把课内实践时间当作全部开发时间。
实验与数据要求
开发集用于调整方法，测试集用于最终比较，二者应分开。来自同一原文、同一模板或其改写的样本应尽量放在同一划分中，避免信息泄漏。正式测试前固定模型、提示词、参数和评分口径。
各题列出的样本数量为建议规模。根据预算调整时，应在正式测试前说明理由并确认，不能只挑选少数成功样例。每项指标需写明分子、分母、判定规则及样本数；失败、超时和格式错误应计入统计。
成果与判断依据
每组须提供可运行成果、对照实验、独立测试结果和失败或边界案例。判断依据应来自原始资料、人工核对、数据库执行、规则程序或隐藏测试，不能让模型生成答案后再由同一模型自行证明正确。

选题注意事项
01至05侧重应用流程与数据处理，06至10侧重工具执行及可靠性，11至15侧重方法对照、模型机制和成本。每个课题的基础实现均须完成，额外功能应在基础成果稳定后再考虑。
资源链接用于学习实现方法，不代表可以直接提交现成项目。引用教程、代码和模型时须注明来源并遵守许可；旧教程的 API 写法应按当前官方文档调整，不要求购买课程证书或使用特定商业平台。

提交材料
1．可运行源码与运行说明，包括依赖版本、配置方法和最小演示数据，不提交 API 密钥。

课题01 有据可查的校园制度问答助手
方向　应用开发　　主要内容　检索与证据
要解决的问题　面对同学的制度咨询，系统怎样给出有原文依据的回答，并在资料不足时停止猜测？
任务范围　选择图书馆借阅、竞赛申报等一个窄领域，整理10至20份公开文件。记录文件来源、日期、版本和页码，使用普通电脑建立检索库。
基础实现要求
1．实现文档解析、切分、检索和基于资料的回答，保留检索片段与答案之间的关联。
2．在答案中给出可点击的来源及页码或条款，支持核对原文；对缺少依据的问题说明无法确定。
3．从条款切分、关键词与向量混合检索、版本过滤中选择适当改进，避免旧文件覆盖现行规定。
对照实验　固定同一生成模型，比较直接提问、普通检索增强问答、加入所选改进后的问答。关键词直接检索原文可作为补充基线。开发时可以调整切分与检索参数，正式测试前固定配置。
建议测试与验收　准备约60道独立测试题，包含正常问题、文件未提及的问题和新旧版本冲突。分别统计答案正确率、引用支持率、不可回答题的正确拒答率，并记录每题 Token 和耗时。引用支持率指所引用原文确实支持对应结论的比例。
课题成果　交付可查询原文的问答程序、版本化知识库、测试结果和错误案例。展示一个正确引用案例及一个资料不足案例。
资源与边界　嵌入和检索结果本地缓存，每次只发送少量相关片段。只用公开资料，不接入个人档案；页面提示教学原型的回答需以官方原文为准。

课题02 竞赛与讲座通知整理器
方向　应用开发　　主要内容　结构化抽取
要解决的问题　怎样把写法不同的通知转成可筛选的数据表，同时避免把缺失信息补成错误事实？
任务范围　收集公开或自行编写的竞赛、讲座通知。固定名称、类型、举办时间、地点、报名截止日期和参加条件六类字段，明确一条通知包含多个活动时的拆分规则。
基础实现要求
1．实现通知输入、字段抽取和表格展示，使用 JSON Schema 或等价的数据结构约束输出。
2．保存字段对应的原句，缺失字段记为空值；对日期格式、报名时间与举办时间进行程序校验。
3．对不合法输出实施有限次纠错，提供人工确认及 CSV 导出功能，不自动写入真实日历。
对照实验　比较正则或关键词规则、普通提示词抽取、结构化输出加校验的方案。使用同一批通知和字段定义，记录哪些错误来自格式、字段理解或日期判断。
建议测试与验收　准备约60条测试通知，覆盖字段缺失、多个活动和日期变更。统计字段级正确率、整条记录完全正确率、JSON 合法率和缺失字段误填率。不能只凭输出能被程序解析就判定任务成功。
课题成果　交付通知整理程序、字段规范、带证据的结果表和批量评测脚本。演示一条缺失报名截止日期的通知，并说明系统如何处理。
资源与边界　优先每条通知一次短文本 API 调用，结果缓存后复用。去除不必要的个人联系方式；人工金标准不能直接采用未经核对的模型输出。

课题03 表格截图读取与数值核对助手
方向　应用开发　　主要内容　图文处理与核算
要解决的问题　表格截图中的数字是否被正确识别、放回正确行列，并用于正确计算？
任务范围　基础版仅处理清晰的简单表格截图，不扩展到任意长 PDF、复杂科研图或手写稿。准备20至30张测试图片及人工核对的单元格数据，每张设置合计、排序或差值问题。
基础实现要求
1．使用本地 OCR 识别文字与位置，保留原图和识别结果；由文本大模型整理行列关系并输出结构化表格。
2．使用 Python 执行求和、排序和差值计算，回答时显示来源行列或图片区域。
3．每张图片只抽取一次，后续问题复用结构化结果，并保留需要人工核对的识别疑点。
对照实验　比较把 OCR 纯文本直接交给模型回答，与先还原结构化表格再由程序计算的方案。仅在额外视觉 API 额度获确认后，才增加直接看图的对照，不作为基础要求。
建议测试与验收　分别统计关键数字识别正确率、行列配对正确率、计算题正确率和来源定位正确率。将错误分为识别错误、结构错误和计算错误；已正确识别的数值应由程序精确核算。
课题成果　交付截图处理与核对程序、人工标准表格、结果浏览页和分阶段误差分析。展示至少一个识别错误如何影响最终结论的案例。
资源与边界　OCR 和数值计算在 CPU 运行，只向文本 API 发送必要识别结果。基础版不需要视觉 API，不上传含真实证件或个人敏感信息的图片。

课题04 自然语言查询校园活动数据库
方向　应用开发　　主要内容　SQL 生成与验证
要解决的问题　怎样让大模型把问题转成查询，并让最终统计数字来自数据库的实际执行结果？
任务范围　使用虚构数据建立 SQLite 数据库，包含活动、场地、报名等4至6张关联表。支持筛选、排序、统计和关联查询，明确各字段含义与表间关系。
基础实现要求
1．实现自然语言提问、SQL 生成、数据库执行和结果解释，界面同时展示 SQL 与实际结果。
2．对含糊问题先澄清；实现相关表选择或少量示例，并在执行报错后最多修正一次。
3．由程序设置只读连接、语句限制、结果行数和超时控制，禁止任意写入与外部扩展。
对照实验　比较一次生成 SQL，与加入相关表选择或执行反馈修正的方案。固定数据库、问题和模型，按执行结果比较答案，不要求与标准 SQL 字符串逐字相同。
建议测试与验收　准备约50道独立测试题，覆盖常规查询、JOIN、聚合、含糊要求和写操作请求。统计执行成功率、结果正确率、澄清表现、写操作阻断情况及平均调用次数。
课题成果　交付模拟数据库、查询程序、标准查询结果、失败 SQL 和修正轨迹。演示正常统计、问题澄清和写操作被阻断三种情况。
资源与边界　只连接教学模拟库，不能使用真实教务数据库。权限必须由程序实现，不能只依赖提示词。正常查询一次调用，失败修正次数受限。

课题05 带时间戳证据的录音纪要助手
方向　应用开发　　主要内容　语音转写与事实核对
要解决的问题　纪要中的决定和待办能否回到原录音核对，且不会凭空补出负责人或截止日期？
任务范围　使用6至8段取得同意的短录音，每段约3至5分钟。人工核对重要事实和相应时间段；划分开发录音与独立测试录音，不要求实时处理、声纹识别或说话人分离。
基础实现要求
1．用本地小型语音识别模型生成带时间戳的转写，保留原始转写并缓存。
2．按议题整理决定、待办和待确认事项，为每条重要结论绑定原句及时间段。
3．未明确说明的负责人和截止日期保留未知，支持从纪要定位或回听相关音频。
对照实验　比较完整转写直接摘要，与分段整理并绑定证据的方案。另用人工修正的转写运行同一流程，区分语音识别错误与大模型整理错误。
建议测试与验收　对测试录音的重要决定和待办统计精确率与召回率，检查虚构、遗漏和错误归属。抽样计算中文字符识别错误率，并统计证据时间段能否包含对应原话。记录 CPU 处理耗时。
课题成果　交付可定位证据的纪要程序、授权说明、转写与人工核对记录，以及识别误差传播分析。至少展示一个数字或人名转写错误的处理过程。
资源与边界　录音离线转写一次，文本 API 处理短片段。时间戳须来自转写或人工核对，不能让模型猜测；未经同意不得上传或公开录音。

课题06 带确认与冲突处理的模拟预约Agent
方向　智能体与可靠性　　主要内容　工具调用与权限
要解决的问题　助手怎样根据工具结果完成预约，并保证用户没有确认时不会产生实际写入？
任务范围　自建虚构自习室和日程数据，提供查询空闲、检查方案和提交预约三个工具。问题可包含日期、人数和时段偏好，不接入真实预约账号。
基础实现要求
1．实现工具参数校验和清楚的预约状态，缺失必要条件时先询问用户。
2．根据容量不足、全部冲突等工具反馈修正方案，得到明确确认后才能提交。
3．由程序限制提交权限并避免重复写入，保存每次工具请求、返回结果和最终状态。
对照实验　比较一次性产生固定操作步骤，与逐步读取工具反馈后调整操作的方式。每项任务最多5次工具调用，最多2次失败恢复；超出上限应停止并说明原因。
建议测试与验收　准备约30个独立测试情境，覆盖正常预约、时间缺失、容量不足、全部冲突、拒绝确认和重复提交。统计任务成功率、错误预约数、无确认写入数和平均调用次数。
课题成果　交付可回放执行轨迹的模拟预约程序、场景测试集和状态变化记录。验收时同时检查最终数据库状态，不能只看模型是否说出预约成功。
资源与边界　全部操作在本地模拟环境执行。无确认提交和重复写入应被程序阻断；不发送真实通知，不保存校园账号密码。

课题07 测试驱动的Python函数修复助手
方向　智能体与可靠性　　主要内容　代码生成与执行反馈
要解决的问题　测试反馈是否能够帮助模型真正修复错误，而不只是生成看似合理的补丁？
任务范围　只处理短小纯函数，例如列表处理、字符串处理和边界条件错误。每题提供需求、错误函数、可公开测试与隐藏测试，隐藏测试仅用于最终判定。
基础实现要求
1．实现补丁生成、隔离执行公开测试、失败反馈和有限修正，保留每轮代码与日志。
2．禁止模型修改测试或读取隐藏测试，避免修复过程破坏原有正确功能。
3．使用无网络、受资源限制的隔离执行器，不向其中传入宿主目录、API 密钥或个人文件。
